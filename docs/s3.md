# S3 operator guide

`ManifestS3DagBundle` gives Airflow versioned Dag bundles from a mutable S3 folder.
It keeps the Dag source read-only. An automatic dag processor or an explicit
publisher mirrors the current folder into local staging, then publishes an
immutable, content-addressed snapshot to `published_root` — an `s3://` prefix,
which is the recommended mode because no host needs a shared filesystem (see
[Object-store published root](#object-store-published-root)), or a shared
filesystem path as a fallback. Airflow parses and executes only validated cache
copies of those snapshots.

## Installation

Install the S3 extra on each automatic dag-processor or explicit publisher host.
Use the same explicit Airflow version as the deployment:

```bash
python -m pip install \
  "apache-airflow==3.3.0" \
  "airflow-manifest-bundle[s3]==0.3.0"
```

The extra installs `apache-airflow-providers-amazon`. The minimum supported provider
version is 9.10.0, which introduced the stock `S3DagBundle` used as the compatibility
reference. An explicit-mode dag processor that only reads `published_root` can use
the base package without the S3 extra.

## Configuration

```ini
[dag_processor]
dag_bundle_config_list = [
    {
      "name": "my_dags",
      "classpath": "airflow_manifest_bundle.s3.ManifestS3DagBundle",
      "kwargs": {
        "bucket_name": "airflow-dags",
        "prefix": "production/",
        "aws_conn_id": "aws_default",
        "published_root": "s3://airflow-dags/releases",
        "refresh_interval": 30,
        "source_stability_seconds": 30,
        "deployment_marker_key": ".ready"
      }
    }
  ]
```

`bucket_name` and `published_root` are required. `prefix` defaults to the bucket
root. `aws_conn_id` defaults to `aws_default`, which preserves stock Airflow
behavior and its normal fallback to the boto3 credential chain.

`published_root` accepts an `s3://bucket/prefix` URL (recommended for an S3
source) or a filesystem path. Use a filesystem path only for the two fallback
situations: workers that must run without any cloud credentials, or an object
store without conditional-write support. The bundle writes an info log when an S3
source publishes to a filesystem root. A `gs://` published root is rejected:
cross-cloud publication is not supported.

The manifest extensions are:

- `auto_publish`: publish during each unpinned refresh. The default is `true`. Set it
  to `false` when a deployment pipeline runs the explicit publisher command.
- `source_stability_seconds`: how long one remote observation must remain unchanged.
  The default is `refresh_interval`. It applies only to automatic publication.
- `allow_empty_source`: permit a release with no included files. The default is
  `false`.
- `deployment_marker_key`: a relative object key below `prefix` that the deployment
  process writes last. When you configure it, the object is required.
- `max_file_count`: maximum included objects. The default is 10,000.
- `max_file_size_bytes`: maximum bytes in one included object. The default is
  104,857,600 (100 MiB).
- `max_total_size_bytes`: maximum bytes in all included objects. The default is
  1,073,741,824 (1 GiB).
- `published_root_conn_id`: the AWS connection for an `s3://` published root. The
  default is the store's standard connection resolution. It is invalid for a
  filesystem root.

Keep a filesystem `published_root` on durable shared storage; it must not overlap
`dag_bundle_storage_path`. For an `s3://` root, plan retention with lifecycle rules
instead (see [Object-store published root](#object-store-published-root)).

## What the bundle stores

Each dag-processor host has these disposable paths below Airflow's bundle base
folder:

```text
_s3_source/                 mutable S3 mirror
_s3_source_state.json       remote change-token and mirror cache
versions/                   validated Airflow cache copies
```

The published root is authoritative:

```text
versions/<bundle>/sha256-<hex>/           immutable snapshots
refs/<bundle>/latest.json                 current release reference
_locks/<bundle>.lock                      publication lock (filesystem roots only)
_state/<bundle>/auto-publish.json         shared stability candidate
```

An object-store published root uses the same layout under its prefix, without
`_locks/`: the reference and candidate documents are protected by conditional
writes, and the embedded snapshot manifest object is written last, so its presence
commits the snapshot.

The mirror can be deleted at any time. The next automatic refresh or explicit
publication rebuilds it. Do not back it up, mount it as a Dag folder, or let any
Airflow component execute from it.

The S3 source contains only the current mutable state. It cannot recover an old
bundle version after the local cache disappears. Back up or replicate
`published_root` for as long as retries, reruns, deferred tasks, callbacks, or cleared
Dag runs can request an old `DagRun.bundle_version`.

## Read-only IAM for the Dag source

An automatic dag processor or an explicit publisher host needs:

```text
s3:ListBucket
    constrained to the configured prefix

s3:GetObject
    on objects below the configured prefix
```

Add `kms:Decrypt` when the objects use SSE-KMS.

Against the Dag source, the bundle does not call `PutObject`, `DeleteObject`,
`ListBucketVersions`, or `GetObjectVersion`. A deployment system writes the Dag
objects and optional marker; Airflow does not. (An object-store `published_root` is
a separate prefix that publishers do write — see the next section. The Dag source
stays read-only in every mode.)

With a filesystem `published_root`, dag processors with `auto_publish` set to
`false` need no S3 permissions or AWS connection. The explicit publisher host holds
those permissions instead. Workers that only initialize pinned versions also need no
S3 permissions. These processes need read access to `published_root` and write
access to their Airflow bundle cache. Pinned initialization does not create an S3
hook, list the bucket, read the mirror, or read `latest.json`.

## Object-store published root

Set `published_root` to an `s3://bucket/prefix` URL to keep the releases in S3
instead of a shared filesystem. The layout and behavior described in this guide stay
the same; only the transport and the coordination primitives change. The optional
`published_root_conn_id` kwarg selects the AWS connection for the artifact store
(default: the standard connection resolution). On workers, prefer credentials the
default AWS chain can resolve — an instance profile or IRSA — because bundle
initialization runs before task context.

Requirements and permissions:

```text
Publisher (automatic dag processor, or the explicit publisher host)
    Dag source prefix:      s3:ListBucket, s3:GetObject          (read-only, as above)
    releases prefix:        s3:PutObject, s3:GetObject
    releases prefix:        s3:GetObject on the source prefix by the store's
                            principal enables server-side copies (optional)

Worker / triggerer (pinned initialization)
    releases prefix:        s3:GetObject
    nothing else — no listing, no source access

Consume-only dag processor (auto_publish false, explicit releases)
    releases prefix:        s3:GetObject
```

Add `kms:Decrypt`/`kms:GenerateDataKey` when the prefixes use SSE-KMS.

Publication requires conditional-write support (`If-Match`/`If-None-Match` on
`PutObject`). AWS S3 supports it; an S3-compatible store without it fails the first
publication with a clear error, and consume-only use still works.

When the Dag source and the releases prefix share an S3 endpoint and the store's
principal can read the source objects, publication copies each file server-side,
pinned to the exact object version the manifest hashed (`CopySourceIfMatch`); no
file content moves through the dag processor. Any copy failure falls back to an
upload of the prepared mirror copy automatically — the published bytes always match
the manifest either way, and workers hash-verify every file at materialization.

Retention and immutability:

- Prune old releases with a lifecycle rule on `versions/` under the releases prefix.
  The rule must keep any version that a Dag run can still request — the same
  contract as filesystem pruning.
- A crash between file uploads and the manifest write leaves an uncommitted version
  prefix. It is invisible to consumers and completed by a later publication of the
  same content; reclaim abandoned ones with an age-based lifecycle rule if the
  storage matters.
- To make snapshots tamper-proof rather than tamper-evident, deny overwrites and
  deletes on `versions/` with a bucket policy, or use S3 Object Lock. Workers detect
  any modified object at materialization regardless, and fail closed.

## Deployment boundary

The stability window filters short-lived changes, but it is not a transaction. A
partly uploaded folder can remain unchanged long enough to look stable.

`deployment_marker_key` is relative to `prefix`. For this configuration:

```ini
"bucket_name": "airflow-dags",
"prefix": "production/",
"deployment_marker_key": ".ready"
```

the marker object is:

```text
s3://airflow-dags/production/.ready
```

The marker is not a Dag file. Its value is not part of the bundle version, and the
bundle does not interpret it. Give each deployment a new unique value, such as a Git
commit SHA, CI run ID, or deployment UUID. The change lets the bundle distinguish a
completed deployment from later object changes.

For a strong release boundary:

1. Upload or replace all Dag objects below the configured prefix.
2. Delete objects that are not part of the new release.
3. Write or replace `deployment_marker_key` last with a new value.

For example, an explicit publication pipeline can run:

```bash
set -euo pipefail

BUCKET=airflow-dags
PREFIX=production/
MARKER_KEY=.ready
DEPLOYMENT_ID="${GIT_COMMIT_SHA:?GIT_COMMIT_SHA must be set}"

aws s3 sync ./dags "s3://${BUCKET}/${PREFIX}" \
  --delete \
  --exclude "${MARKER_KEY}"

printf '%s\n' "${DEPLOYMENT_ID}" |
  aws s3 cp - "s3://${BUCKET}/${PREFIX}${MARKER_KEY}" \
    --content-type text/plain

airflow-manifest-bundle publish-s3 my_dags --output json
```

Set `BUCKET`, `PREFIX`, and `MARKER_KEY` to the exact values in the bundle
configuration. The `--exclude` option keeps that marker in place while the files
change. The final `aws s3 cp` replaces the same marker only after `aws s3 sync`
succeeds.

The bundle reads the marker before and after each inventory. It excludes the marker
from the mirror and manifest. If Dag objects change but the marker recorded in the
current release does not change, the bundle keeps the current release. The first
release can use an existing stable marker.

When `deployment_marker_key` is configured but the object is missing, explicit
publication fails. Automatic publication keeps the current release; if no release
exists, initialization reports the missing marker and retries later. The bundle
never creates or updates this object. The publisher keeps its read-only
`s3:GetObject` and `s3:ListBucket` access.

Do not modify release objects after the marker write. The marker protocol cannot
repair a deployment process that violates this order.

This deployment marker is different from a cache validation marker. A deployment
marker is an S3 object written by the deployment system. A validation marker is a
local `.sha256-<hex>.validated` file that the bundle writes after it validates a
cache copy.

## Explicit publication

Set `auto_publish` to `false` in the bundle configuration:

```ini
"kwargs": {
  "auto_publish": false,
  "bucket_name": "airflow-dags",
  "prefix": "production/",
  "aws_conn_id": "aws_default",
  "published_root": "/mnt/shared/airflow-bundles",
  "deployment_marker_key": ".ready"
}
```

After the deployment tool writes the Dag objects and optional marker, run:

```bash
airflow-manifest-bundle publish-s3 my_dags --output json
```

After the first release, use the current version as an ordering guard:

```bash
airflow-manifest-bundle publish-s3 my_dags \
  --expected-current-version sha256-<hex> \
  --output json
```

The command gets the bucket, prefix, connection, limits, and marker from the Airflow
bundle configuration. It does not write to S3. It holds the host's Airflow bundle
lock while it synchronizes and publishes the mirror. It confirms the local mirror
and remote inventory before it updates the release reference.

The explicit command is the deployment boundary, so it does not wait for
`source_stability_seconds` and does not write automatic candidate state. Run it only
after the source delivery is complete. The command rejects a bundle that still has
`auto_publish` enabled.

## Synchronization and integrity

The adapter validates every listed key before a download. It rejects absolute or
parent-relative paths, empty components, backslashes, control characters,
duplicates, and file/directory collisions. It ignores S3 directory markers and the
same files that local manifest publication ignores: `.git`, `__pycache__`, `.pyc`,
and `.airflow-bundle-manifest.json`.

For each included object, the mirror state stores size, last-modified value, ETag,
and local metadata. ETag is only a remote change token. It is never an artifact
hash. A changed token forces a download even when the object has the same size.
Before a fresh process reuses a mirror file for publication, it verifies the local
SHA-256 value from mirror state. A mismatch forces a new download. After the process
confirms one source observation and published snapshot, unchanged refreshes stay on
the metadata-only fast path.

After a changed mirror sync, the adapter lists S3 again and requires the same
inventory. Publication then calculates SHA-256 from local bytes, copies those bytes
to an immutable snapshot, verifies the copy, confirms the local mirror and remote
observation again, and replaces the release reference last.

If one of these operations fails during automatic publication, the bundle logs the
error and keeps the current release active. During explicit publication, the command
exits with an error and leaves the current release reference unchanged.

## Capacity and recovery

Plan space for:

- one current S3 mirror per automatic dag-processor or explicit publisher host;
- every retained immutable snapshot in `published_root`;
- Airflow's retained local cache copies.

The default source limits stop an unexpected prefix from consuming unbounded local
space. Set higher limits only after you include the mirror, published snapshots, and
local cache copies in capacity planning.

To recover a broken mirror, stop concurrent publication on that host and remove only
the bundle's `_s3_source` folder and `_s3_source_state.json`. The next automatic
refresh or explicit command downloads a fresh validated inventory.

To recover a cache, remove the affected cache version and its validation marker.
Pinned or unpinned initialization rematerializes it from `published_root`.

If a published snapshot is missing, restore that exact `sha256-<hex>` directory from
backup. Copying the current S3 prefix is not sufficient unless its bytes happen to
produce the requested historical version.

The S3 source identity contains the endpoint, bucket, and normalized prefix. An
endpoint change stops publication because a different endpoint can expose a
different object store with the same bucket name. Use this procedure for a planned
endpoint migration:

1. Stop all unpinned dag processors and explicit publisher commands for the bundle.
2. Verify that the new endpoint exposes the intended bucket and prefix.
3. Move `refs/<bundle>/latest.json` to a backup outside the `refs` folder. Do not
   change its source metadata in place.
4. Start one automatic dag processor, or run `publish-s3` in explicit mode.
5. Verify the new release, then start the other dag processors.

Pinned bundles do not read the release reference and can still recover retained
versions during this procedure. If the new endpoint fails, stop the publisher,
restore the old endpoint and release reference, and then restart the publishers.
